## SECTION 1 — Pattern Overview

### 1.1 What Is This Pattern?
Also called **Floyd's Cycle Detection** or the "Tortoise and Hare" algorithm, Fast & Slow Pointers uses two pointers traversing the same sequence (usually a linked list, sometimes an array treated as a functional graph) at **different speeds** — typically slow moves 1 step, fast moves 2 steps per iteration. The relative speed difference lets you detect cycles, find midpoints, or detect specific offsets **without extra memory**.

### 1.2 Why Was This Pattern Invented?
Detecting a cycle in a linked list naively requires storing every visited node in a hash set — O(n) space. Robert Floyd's insight (1967) was that **if a cycle exists, a faster-moving pointer must eventually "lap" a slower one inside the cycle**, exactly like two runners on a circular track — meaning you can detect the cycle in O(1) space by simply checking if the two pointers ever meet.

### 1.3 Real Intuition Behind The Pattern
On a circular running track, a faster runner will eventually catch up to and pass a slower runner, no matter where they started, as long as the track is a loop. If the track were a straight, non-looping road, the faster runner would just finish first and never "meet" the slower one again. This binary outcome — **meet ⇒ cycle exists; reach the end ⇒ no cycle** — is the entire basis of the pattern.

### 1.4 Mental Model
Think of `slow` as marking "elapsed distance `d`" and `fast` as marking "elapsed distance `2d`." If they're ever at the same node, the gap between their distances (`d`) must be a multiple of the cycle length — a purely arithmetic consequence of modular arithmetic on a cycle.

### 1.5 Visual Explanation
```
List:  1 → 2 → 3 → 4 → 5
                ↑         ↓
                8 ← 7 ← 6

slow: 1 → 2 → 3 → 4 → 5 → 6 → 7 ...
fast: 1 → 3 → 5 → 7 → 4 → 6 → 8 ...
                          
Eventually slow and fast land on the SAME node inside the loop (3→4→5→6→7→8→3...) — cycle confirmed.
```

### 1.6 Simple Analogy
Two friends jogging on a circular park track, one twice as fast as the other — if the track loops, the faster friend eventually laps the slower one and they high-five mid-lap. If it's a straight path with an end, the faster friend just finishes and waits at the exit — no meeting happens mid-path.

### 1.7 When Should I Immediately Think About Using This Pattern?
- Linked list problems mentioning **"cycle," "loop," "starts of the cycle."**
- "Find the **middle** of a linked list" in a single pass.
- "Detect a duplicate number" in an array where values point to indices (functional graph cycle).
- "Determine if a sequence eventually repeats" (e.g., Happy Number problem).

## SECTION 2 — Recognition Guide

### 2.1 Keywords In Problem Statement
| Keyword | Signal |
|---|---|
| "cycle" / "loop" | Direct signal for Floyd's algorithm |
| "middle of the linked list" | Fast/slow with fast moving 2x |
| "starts of a cycle" | Floyd's algorithm phase 2 (finding cycle entry) |
| "happy number" / "eventually repeats" | Cycle detection over a functional sequence, not a literal linked list |
| "duplicate number, values in range [1,n]" | Array-as-linked-list cycle detection |
| "without extra space" | Rules out hash-set based visited tracking, strongly implies Fast & Slow |

### 2.2 Hidden Hints
A problem defined over a **sequence generated by repeatedly applying a function** (`x = f(x)`) — even if it doesn't mention linked lists at all — is very often solvable via Fast & Slow (e.g., LeetCode's Happy Number, Find the Duplicate Number).

### 2.3 Interview Clues
Interviewer explicitly rules out extra space ("can you do it in O(1) space?") after you propose a hash-set solution — the strongest possible nudge toward Fast & Slow.

### 2.4 Common Trick Words
"Detect if," "determine the entry point of," "kth node from the end" (a fast/slow variant with a fixed offset gap rather than 2x speed).

### 2.5 What Interviewers Expect
Correct implementation of both phases of Floyd's algorithm (cycle **detection**, then cycle **entry point**), and the mathematical justification for why the entry-point-finding phase works (not just "it's a known trick").

### 2.6 When NOT To Use This Pattern
- You need **random access** or need to examine all elements (not just detect a structural property) — arrays with direct indexing may not need this trick at all.
- The structure is **not a chain/sequence with a single "next" pointer** (e.g., trees with multiple children, general graphs) — use standard graph cycle detection (DFS with colors / Union-Find) instead.
- You need the **actual set of visited nodes**, not just cycle existence — then O(n) space hashing might be simpler and equally acceptable if space isn't constrained.

```
   │
  Yes → after meeting, reset one pointer to head, move both

```
**Why:** Fast & Slow is strictly about O(1) space cycle/midpoint detection over chain-like structures; anything requiring full traversal history or multi-branch structures needs a different tool.

## SECTION 4 — Why This Pattern Works

### 4.1 Mathematical Proof of Meeting (Cycle Detection)
Let the list have a non-cyclic prefix of length `μ` and a cycle of length `λ`. After `t` steps, `slow` is at position `μ + ((t - μ) mod λ)` once inside the cycle, and `fast` is at position equivalent to `2t`. They meet when `2t ≡ t (mod λ)` for `t ≥ μ`, i.e., `t ≡ 0 (mod λ)`. Since `t` increases by 1 each step, some multiple of `λ` greater than or equal to `μ` will always be reached in finite steps — **guaranteeing a meeting point exists if and only if a cycle exists.**

### 4.2 Proof of Entry-Point-Finding Phase
At the meeting point, `slow` has traveled `μ + a` steps (where `a` is distance traveled inside the cycle) and `fast` has traveled `2(μ + a)` steps. Since fast has looped around some integer number of times `k`, we get `2(μ+a) - (μ+a) = kλ`, i.e., `μ + a = kλ`, so `μ ≡ -a (mod λ)`, i.e., `μ ≡ (λ - a) (mod λ)`. This means: if you place one pointer back at the **head** (distance `μ` from cycle start) and leave the other at the **meeting point** (distance `λ - a` from cycle start, equivalently), and move both one step at a time, **they will meet exactly at the cycle's entry node** after `μ` steps. This is a beautiful, non-obvious modular arithmetic result — memorize the *proof sketch*, not just the trick.

### 4.3 Logical/Intuitive Argument
Two runners on a track, one twice as fast: the gap between them changes by exactly 1 lap-distance-unit each cycle iteration once both are on the loop, so the gap must eventually become 0 (a full lap difference) — they must meet.

### 4.4 Correctness of "Find the Middle" Variant
When `fast` reaches the end (`null` or one before), `slow` has traveled exactly half the distance, because fast always travels exactly twice as far in the same number of steps — a direct, non-modular consequence of the 2x speed ratio, no cycle needed.

## SECTION 5 — Algorithm Framework

### 5.1 Step-by-Step Framework (Cycle Detection + Entry Point)
1. Initialize `slow = head`, `fast = head`.
2. Loop while `fast` and `fast.next` are non-null: `slow = slow.next`; `fast = fast.next.next`.
3. If `slow == fast` at any point, a cycle exists — break out to phase 2.
4. If the loop exits naturally (`fast` or `fast.next` becomes null), no cycle exists.
5. **Phase 2 (entry point):** reset `slow2 = head`; move `slow` and `slow2` one step at a time until `slow == slow2` — that node is the cycle's entry point.

### 5.2 General Template (Language-Independent Pseudocode)
```
function hasCycle(head):
    slow = head
    fast = head
    while fast != null and fast.next != null:
        slow = slow.next
        fast = fast.next.next
        if slow == fast:
            return true
    return false

function findCycleStart(head):
    slow = head
    fast = head
    while fast != null and fast.next != null:
        slow = slow.next
        fast = fast.next.next
        if slow == fast:
            ptr = head
            while ptr != slow:
                ptr = ptr.next
                slow = slow.next
            return ptr           # cycle entry node
    return null                  # no cycle
```

### 5.3 Find-Middle Variant
```
function findMiddle(head):
    slow = head
    fast = head
    while fast != null and fast.next != null:
        slow = slow.next
        fast = fast.next.next
    return slow                  # middle node (upper-middle if even length)
```

### 5.4 Interview Thinking Process
1. "This is a chain-structured traversal — I'll use two pointers at different speeds to avoid O(n) extra space."
2. "If a cycle exists, the fast pointer will eventually lap the slow one — I can prove this via modular arithmetic on the cycle length."
3. "If I also need the cycle's entry point, I'll reset one pointer to head and advance both at equal speed — they'll meet exactly at the entry, which I can justify with the μ ≡ -a (mod λ) relation."
4. "Let me dry-run on a small list with a known cycle to validate indices before finalizing."

## SECTION 6 — Time & Space Complexity

| Case | Time | Space | Why |
|---|---|---|---|
| Worst Case | O(n) | O(1) | Fast pointer traverses at most 2n nodes before either exiting or meeting slow |
| Average Case | O(n) | O(1) | Independent of cycle position — bounded by list length + cycle length |
| Best Case | O(1) (immediate cycle at head) to O(n) | O(1) | Still requires at least one comparison |
| Amortized | O(n) total across both phases (detection + entry-finding) | O(1) | Phase 2 adds at most another O(n) traversal, still linear overall |

## SECTION 7 — Edge Cases

| Edge Case | Example | Handling |
|---|---|---|
| Empty list | `head = null` | Immediately return false/null |
| Single node, no self-loop | `[5] → null` | Loop condition fails immediately, no cycle |
| Single node with self-loop | `[5] → itself` | `fast` and `slow` both point to node 5 immediately on next iteration — cycle detected correctly |
| Two nodes forming a cycle | `1 → 2 → 1` | Meeting occurs within 2 iterations — verify with dry run |
| Cycle length 1 vs list length 1,000,000 | huge non-cyclic prefix | Still O(n) — proof in §4.1 doesn't depend on cycle length being small |
| No cycle, even-length list | `[1,2,3,4]` | `fast` reaches null cleanly, loop exits, no false positive |
| No cycle, odd-length list | `[1,2,3]` | `fast.next` becomes null exactly when expected, exits safely |
| Middle-of-list with even length | `[1,2,3,4]` | Convention: fast/slow lands on second-middle element (index 2, value 3) — clarify with interviewer which "middle" is expected |

**Common mistakes:** checking `fast != null` but forgetting `fast.next != null` (causes null pointer dereference on `fast.next.next`); assuming a cycle always starts at the head (rarely true — must run phase 2 to find the actual entry).

## SECTION 8 — Pros & Cons

**Advantages:** O(1) space cycle detection (versus O(n) with a hash set); simultaneously finds midpoints without needing to know the list length in advance; elegant, provably correct via clean modular arithmetic.
**Disadvantages:** Only works on **single-successor chain structures**; the entry-point-finding phase, while correct, is non-obvious and easy to misremember without understanding the proof.
**Trade-offs:** Fast & Slow (O(1) space) vs Hash Set (O(n) space, arguably more intuitive to explain) — prefer Fast & Slow when space is constrained or when the interviewer explicitly asks for O(1) space.
**Limitations:** Doesn't generalize to graphs with multiple outgoing edges per node — that requires DFS-based cycle detection with color marking.
**Inefficient when:** N/A for its core use case — it is already asymptotically optimal for chain-based cycle detection; there's no faster known approach for this exact problem shape.

## SECTION 10 — Interview Strategy

**How seniors answer:** They state the O(1) space constraint proactively, explain the "runners on a track" intuition before coding, and — critically — can derive the entry-point-finding phase's correctness on the whiteboard using the `μ ≡ -a (mod λ)` relationship rather than reciting it as a memorized trick.

**How juniors answer:** They often only know "move slow by 1, fast by 2, if they meet there's a cycle" but cannot explain *why* resetting one pointer to head and moving both at speed 1 finds the entry point — a dead giveaway under a "why does that work?" follow-up.

**Typical follow-ups:** "Can you find the length of the cycle?" (once inside the cycle, keep one pointer fixed and advance the other until it returns — count steps). "Can you do this with O(n) space instead — which is simpler to explain?" (hash set comparison). "How would this generalize to a graph with multiple next pointers?"

**Optimization questions:** "Is there a way to avoid the second traversal phase?" (No — it's mathematically necessary; discuss why the meeting point alone doesn't tell you the entry point directly).

## SECTION 15 — Common Mistakes

1. Checking only `fast != null` and forgetting `fast.next != null`, causing a null-pointer crash on `fast.next.next`. *Fix:* always guard both conditions in the while loop.
2. Assuming the cycle starts at the head. *Fix:* always run phase 2 (reset to head, advance both at speed 1) to find the true entry point.
3. Confusing "meeting point" with "entry point" — they are almost never the same node. *Fix:* internalize the proof from §4.2.
4. Forgetting edge cases like a single self-looping node or a two-node cycle. *Fix:* explicitly dry-run these before finalizing.
5. Misapplying Floyd's to multi-successor structures (trees, general graphs) where each node has more than one "next." *Fix:* recognize the pattern only applies to single-successor chains.

**Why people fail:** they memorize "slow moves 1, fast moves 2" without understanding the modular arithmetic that guarantees a meeting occurs and separately guarantees the entry-point trick — under a "why" follow-up or a slightly modified variant (e.g., cycle length, kth node in cycle), memorization alone breaks down.

## SECTION 16 — Optimization Techniques

- **Time:** No further asymptotic optimization exists — O(n) is optimal for this problem shape; focus instead on minimizing constant-factor overhead (avoid redundant traversals).
- **Space:** Already O(1) — the entire point of the pattern versus hash-set alternatives.
- **Readability:** Clearly name pointers `slow`/`fast` (never generic `p1`/`p2`); comment the "why" of the entry-point reset step, since it's the least intuitive part.
- **Interview performance:** Draw the cycle on the whiteboard with `μ` and `λ` labeled before deriving the entry-point logic — visual + algebraic proof together is the strongest signal of seniority.

## SECTION 18 — Dry Runs

### Small Input
`1 → 2 → 3 → 4 → 2` (cycle back to node 2, i.e., μ=1, λ=3)
```
slow=1, fast=1
step1: slow=2, fast=3
step2: slow=3, fast=2  (fast wrapped: 4→2)
step3: slow=4, fast=4  → MEET at node 4
Phase 2: ptr=head(1), slow stays at 4
  ptr=1, slow=4 → not equal → ptr=2, slow=2 → EQUAL → entry point = node 2 ✓ (matches μ=1 prefix: node 1 → entry node 2)
```

### Large Input (Conceptual)
For a list of 100,000 nodes with a cycle of length 500 starting at node 99,000, the meeting point is guaranteed within at most `μ + λ` ≈ 99,500 steps of the fast pointer's traversal (bounded), and phase 2 takes exactly `μ` = 99,000 additional steps — both phases remain strictly O(n) overall.

### Corner Case
Single self-looping node `[5]` where node 5 points to itself: `slow` and `fast` both start at node 5; after one iteration, `slow = node5.next = node5`, `fast = node5.next.next = node5` → they meet immediately (μ=0, λ=1) — correctly detected as a cycle.

## SECTION 19 — Advanced Concepts

- **Cycle length calculation:** once a meeting point is found, keep one pointer fixed and advance the other one step at a time, counting steps until it returns to the fixed pointer — this count is exactly `λ`.
- **Kth node in the cycle:** combine the entry-point result with a modular offset (`(entryIndex + k) mod λ`) to jump directly to any node within the cycle.
- **Functional graph generalization:** any deterministic function `f: S → S` over a finite set `S` (like digit-square-sum for Happy Number) forms a "linked list" where node `x` points to `f(x)` — Floyd's applies directly, revealing that "does this sequence eventually cycle/terminate" problems are secretly linked-list cycle problems.
- **Interview hack:** if you find yourself wanting a hash set "just to be safe," pause and ask whether O(1) space is explicitly required — if so, that's your signal this pattern is expected.

## SECTION 20 — Senior Engineer Insights

Staff engineers recognize Floyd's algorithm as a specific case of a much broader principle: **any deterministic, finite-state, single-successor system must eventually cycle** (pigeonhole principle), and detecting that cycle in O(1) space is possible whenever you can compare "state equality" cheaply. They connect this to real production concerns — for example, reasoning about whether a distributed retry/backoff state machine could loop forever, or whether a configuration-resolution chain (config A includes config B includes config A) has circular dependencies — using the exact same mental model, just applied outside of literal linked lists. Interviewers evaluate whether you can make this leap: from "linked list trick" to "general finite-state cycle detection principle."

```
PATTERN: Fast & Slow Pointers (Floyd's Cycle Detection)
RECOGNIZE: chain/sequence traversal + cycle/middle/repeat detection + O(1) space requirement
TEMPLATE:
    slow = fast = head
    while fast and fast.next:
        slow = slow.next; fast = fast.next.next
        if slow == fast: cycle detected → reset one ptr to head, advance both at speed 1 to find entry
COMPLEXITY: O(n) time, O(1) space

WATCH FOR: null checks on both fast and fast.next, self-loops, entry point ≠ meeting point
DOESN'T APPLY WHEN: multi-successor structures (trees/graphs), need full visited history
```

## SECTION 22 — Revision Notes (5-Minute Review)

- Floyd's = two pointers, different speeds, on a single-successor chain.
- Meeting ⇒ cycle exists (pigeonhole on cycle length).
- Entry point ≠ meeting point — requires phase 2 (reset one pointer to head, equal speed).
- Fast pointer at 2x speed also gives midpoint in one pass, no cycle needed.
- O(1) space is the entire value proposition vs. hash-set O(n) space alternative.
- Generalizes beyond literal linked lists to any deterministic function sequence (Happy Number, Find the Duplicate).
- Doesn't apply to branching structures (trees/general graphs) — use DFS coloring or Union-Find there.

## SECTION 25 — Final Summary

Fast & Slow Pointers (Floyd's Cycle Detection) achieves O(1)-space cycle and midpoint detection over chain-like structures by exploiting a simple but powerful arithmetic fact: **a faster pointer moving through a bounded, looping state space must eventually coincide with a slower one.** The single most important thing to remember forever: **the meeting point tells you a cycle exists, but finding where the cycle actually begins requires a second, distinct phase — reset one pointer to the head and advance both at equal speed, and they will provably meet at the entry point.** This pattern is a specific, elegant instance of a much broader idea — any deterministic, finite-state system eventually cycles — which is why it resurfaces far beyond linked lists, in sequence-generation problems, dependency-resolution chains, and state-machine analysis.
